# Enrolled-runner authority: source review

Date: 2026-09-12
Decision: [#10](https://github.com/09millarda/agents-assemble/issues/10) · Baseline: [ADR 0005](../architecture/0005-native-writer-supervision.md)

## Summary

**Recommendation:** select runner-initiated HTTPS with mandatory client-certificate authentication and an application-owned enrollment registry. Execution durably records accepted receipt bytes, authenticated provenance and its verdict. Do not require separately signed receipt artifacts for this bounded profile. This is a protocol selection, not a vendor, PKI service, hardened daemon or deployment certification.

Use Fleet for enrollment identity/capability lifecycle, Organization and Access for permission to enroll, and Execution for bounded work grants and receipt acceptance. This follows the repository's [context ownership](../../CONTEXT.md) and [native-account boundary](../architecture/0001-control-plane-and-runners.md). Native model login remains independent of service enrollment.

The source facts below establish cryptographic and operating-system limits. The application rules that follow are selected recommendations; RFCs do not define Agents Assemble's tenants, writer obligations or historical receipt policy. Disposable fixture evidence belongs in the companion decision report.

## Small comparison

| Approach | Verified properties | Recommendation for this decision |
| --- | --- | --- |
| Outbound HTTPS with mTLS; server-durable receipt verdict | TLS authenticates the channel endpoints when client authentication is required; its certificate handshake proves private-key possession. Application meaning remains outside TLS. [RFC 8446 §§1, 4.4.3](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.4.3) | Select. Keep operation replay/conflict and receipt history in Execution. TLS transcript authentication is not an independently verifiable receipt artifact. |
| Device authorization plus bearer credentials | Device flow uses separate-browser human authorization and device polling. A bearer token authorizes whoever possesses it without a key-possession proof. [RFC 8628 §§1, 3](https://www.rfc-editor.org/rfc/rfc8628.html#section-3), [RFC 6750 §1.2](https://www.rfc-editor.org/rfc/rfc6750.html#section-1.2) | Optional enrollment UX, not selected for steady-state observer credentials. An approved login does not itself authorize a runner profile or attest a machine. |
| Durable per-receipt asymmetric signatures, over HTTPS | Message signatures protect covered components; the application must establish trusted keys, coverage and replay policy. They do not replace TLS confidentiality. [RFC 9421 §§1.4, 3.2, 7.1.2, 7.2](https://www.rfc-editor.org/rfc/rfc9421.html#section-7.2) | Defer until independently verifiable exports, offline relay or separate observer/transport principals are required. Signatures add key-history and acceptance-time rules and cannot make an untrusted observation true. |

OAuth mTLS is useful precedent, not a requirement to introduce OAuth: RFC 8705 gets the peer certificate from the TLS implementation, checks it against the token binding, distinguishes resource authorization, and leaves secure certificate forwarding through a TLS terminator outside its specification. Its certificate-bound tokens also require replacement when the certificate changes. [RFC 8705 §§3, 6.2–6.5](https://www.rfc-editor.org/rfc/rfc8705.html#section-6.2)

## Recommended ownership and enrollment contract

1. Organization and Access authorizes an authenticated operator for an explicit deployment and organization with `runner:enroll`. Personal/self-hosted deployments provide an operator-controlled equivalent through the same domain port. Being able to authenticate a user is not permission to enroll in every organization.
2. Fleet creates a never-reused runner ID and pending enrollment bound to that deployment, organization, observer identity and approved capability-profile revision. The daemon generates its own service key. The approval records the exact public key and profile; proof of possession accompanies enrollment. A human bootstrap credential is short-lived and single-use, bound to this pending enrollment; it is never a work grant.
3. Fleet maintains authorized certificate fingerprints/key versions, validity, status, authority revision and journal-incarnation continuity. A CA-valid certificate is necessary for the selected PKI profile but insufficient for authorization: only an active registry binding admits the peer. Enrollment grants no writer-control, receipt-settlement or job-start authority by itself.
4. Fleet supplies authenticated, explicitly bounded observer-authorization facts through a public port/event contract. Execution accepts them into its own authorization state and validates current grant/receipt authority in its own transaction. Do not hold a Fleet row lock across an Execution transaction or treat an indefinitely stale Fleet projection as current authority. Authority withdrawal requires an explicit cutoff/acknowledgment protocol; the system cannot claim instantaneous cross-context revocation while using asynchronous replication.
5. Execution alone allocates assignment generations, commits work budgets and issues bounded grants. The runner accepts commands only from its configured Execution service, using the enrollment-bound deployment/organization audience. A runner-generated receipt cannot authorize replacement work. These are refinements of [ADR 0004's grant and obligation ownership](../architecture/0004-runner-assignment-and-checkpoint-recovery.md).

## Recommended transport and identity rules

Require a full authenticated handshake before processing runner commands or receipts; disable TLS early data on these routes. TLS 1.3 explicitly gives 0-RTT weaker replay properties. [RFC 8446 §8](https://www.rfc-editor.org/rfc/rfc8446.html#section-8) Validate the configured server name independently of names the server offers: RFC 9525 requires independently constructed reference identifiers. [RFC 9525 §6.1](https://www.rfc-editor.org/rfc/rfc9525.html#section-6.1)

Derive **authenticated sender** from the TLS peer certificate and registry lookup. Treat payload `issuer`, tenant, runner, host and boot fields as assertions to validate. In the selected direct-observer profile, payload issuer must equal the enrolled logical observer, and the receipt's profile, incarnation and scope must be authorized for that observer. Do not accept an `X-Runner-ID` or forwarded-certificate header from the public request as proof. The fixture should terminate TLS in the accepting service; a future proxy needs a separately authenticated forwarding boundary.

Keep the stable logical observer identity in the immutable receipt. Record the actual TLS certificate fingerprint, authority revision and receive/accept times in server acceptance metadata. This permits exact replay through a legitimately rotated key without editing the original receipt. If a future relay is allowed to submit another observer's receipt, sender and issuer become separate authorities requiring explicit delegation or end-to-end signed evidence; relay transport authentication alone is insufficient.

Use a versioned closed envelope that binds deployment, organization, service audience, runner, observer/profile, incarnation, command/receipt identity, original request digest, exact writer/invocation/scope binding, assignment/generation, input/operation digest and typed outcome. Reject unknown schema versions, duplicate fields and mismatched identities before interpreting the outcome. Canonicalization supports stable identity; it does not authenticate anything. If selecting JCS, implement its Unicode, property ordering and number rules completely; sorted JSON output alone is not a JCS claim. Large counters may be encoded as strings. [RFC 8785 §3](https://www.rfc-editor.org/rfc/rfc8785.html#section-3)

## Recommended lifecycle and historical evidence policy

Certificate validity has a start/end interval, and PKIX separately represents revocation causes such as compromise and supersession. [RFC 5280 §§4.1.2.5, 5.3.1](https://www.rfc-editor.org/rfc/rfc5280.html#section-5.3.1) Neither property supplies Agents Assemble's application revocation policy.

| Event | Required application behavior |
| --- | --- |
| Routine rotation | Register a new key/certificate under the same stable enrollment after authorized proof of possession. Give old/new credentials an explicit bounded overlap; retire the old one. Preserve writer IDs, journal incarnation and accepted history. A failed/ambiguous rotation retries the same enrollment operation rather than creating an implicit second runner. |
| Certificate or observer authority expires | Reject new authenticated writes outside the current validity window. Check registry/authority on every request or stream message, including an already open connection. Renewal needs current authorization; certificate expiry is not evidence of process termination. |
| Key retirement or runner revocation | Withdraw acceptance authority and stop issuing fresh grants. Reject a revoked credential even when it asks to replay an old receipt. Revoke relevant cached/session authorization and bound how long disconnected runners may act through existing grants. Lost connectivity and revocation do not revoke credentials already supplied to native tools or cancel remote effects. |
| Exact replay after rotation, grant expiry or generation replacement | An actively authorized replacement key can query/replay an already accepted receipt for the same logical enrollment. Return the original durable verdict; never repeat its transition. Same receipt ID with changed canonical payload is a conflict. Historical read permission is distinct from permission to submit unseen evidence or start work. |
| First delivery of late evidence | Accept only while the sender currently has explicitly authorized reconciliation authority for that exact historical obligation and incarnation. Original work-grant expiry need not erase evidence authority. A sender-controlled observation timestamp cannot bypass revoked observer authority. |
| Suspected compromise | Retain the original immutable acceptance record for audit. Separately mark affected evidence disputed/quarantined for future recovery, according to an explicit security assessment. An earlier accepted verdict is a record of acceptance, not a guarantee that the key or observer was uncompromised then. |
| Missing/rolled-back journal or replaced daemon | Create a fresh incarnation through explicit enrollment/reconciliation. Retain old unresolved writer obligations. Matching runner name, claimed boot ID or recreated cgroup path cannot restore historical observation authority. Carry over accepted server history; require actual continuity evidence before accepting new reports about old scopes. |

Persist exact canonical receipt bytes/digest, request binding, authenticated provenance, applicable profile/authority revision and verdict in Execution's context-local inbox/state/outbox transaction. Send acceptance only after commit. Lost acknowledgments then reconcile durable state. Retention/backup requirements become part of the guarantee: loss of both authoritative history and trustworthy original scope evidence leaves uncertainty. This is an application design derived from the repository's [durability baseline](../architecture/0003-durable-execution-and-recovery.md), not a promise made by TLS.

## Observation trust and remaining boundary

Linux discretionary file access is based on filesystem user/group IDs and permission bits. Thus an owner-readable key or owner-writable journal ordinarily does not separate two processes running as that owner. [Linux `path_resolution(7)`, Permissions](https://man7.org/linux/man-pages/man7/path_resolution.7.html) Linux Yama documents that classic ptrace permits attachment to same-UID dumpable processes; restricted modes change that behavior, so same-UID memory access must be assessed against the effective policy rather than assumed universal. [Kernel Yama documentation](https://www.kernel.org/doc/html/latest/admin-guide/LSM/Yama.html)

Consequently, an unrestricted native tool sharing the observer's accessible key/journal can impersonate the observer or fabricate its durable state. A separate process, `0600` file, cgroup or signing key does not independently establish a trust boundary. Stolen signing keys also allow fresh signatures. [RFC 9421 §7.3.2](https://www.rfc-editor.org/rfc/rfc9421.html#section-7.3.2)

**Recommendation:** retain an explicitly cooperative/trusted-tool profile for the bounded experiment and keep unrestricted same-UID automatic takeover ineligible. A stronger profile must enforce and validate separation of observer code, key use, journal, launch/stop gates and observation objects, while accounting for every writer capability. A protected signing service must authorize what it signs; exposing an arbitrary-sign API to the workload merely moves the impersonation path. Machine root/operator compromise remains outside a software-only customer-observer guarantee unless a separately designed attestation trust model changes that assumption.

Even a correctly authenticated stopped-scope receipt resolves only its covered local-writer obligation. It cannot establish missing writer coverage, reconcile unknown Git/cloud effects, verify a checkpoint or grant a new attempt. These remain separate [ADR 0005](../architecture/0005-native-writer-supervision.md) obligations and must be exercised independently in the companion fixture.
