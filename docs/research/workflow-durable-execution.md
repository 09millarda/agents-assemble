Research date: 2026-09-15. Sources below are primary documentation, published package contents, and a read-only local protocol smoke test. Proposed Factory behavior is explicitly identified as a design decision; it is not a durability guarantee supplied by a third party.

## DBOS and the Bun boundary

DBOS supplies PostgreSQL functions for enqueueing and messaging. The API and DBOS system schema must use the **same database**, not merely separate databases on the same PostgreSQL server. Functions can participate in the caller's transaction. DBOS owns its schema migrations; do not create SQL views or tracked SQL-function dependencies on functions that DBOS replaces during upgrades. [System database reference](https://docs.dbos.dev/explanations/system-tables)

Use parameterized SQL through Drizzle. This example specifies only the required application fields:

```sql
SELECT dbos.enqueue_workflow(
  workflow_name => 'interpretWorkflowRun',
  queue_name => 'workflow-runs',
  positional_args => ARRAY[$1::json],
  workflow_id => $2,
  app_version => $3,
  application_name => 'factory-coordinator'
);

SELECT dbos.send_message($1, $2::json, $3, $4);
```

**Pinned-source correction:** version 4.27.6 names `send_message`'s fourth parameter `message_id`; the live documentation calls it `idempotency_key`. Positional invocation avoids that mismatch. The shipped migration inserts that value into `message_uuid` with `ON CONFLICT (message_uuid) DO NOTHING`. Use globally unique message identities incorporating the run and command/fact identity. The enqueue function preserves an existing workflow with the same `workflow_id`; it updates its timestamp instead of replacing its arguments. Evidence: `dist/src/sysdb_migrations/internal/migrations.js` in the [4.27.6 package archive](https://registry.npmjs.org/@dbos-inc/dbos-sdk/-/dbos-sdk-4.27.6.tgz).

SQL arguments and messages use portable JSON, which supports ordinary JSON values. Dates travel as RFC 3339 strings. SQL enqueue constructs the portable argument envelope itself; pass the run argument as one element of `JSON[]`, not a hand-built DBOS internal envelope. Validate received messages at the application boundary. [Portable workflows](https://docs.dbos.dev/explanations/portable-workflows)

Messages persist before successful send completion. `recv` consumes messages by topic and can time out; its default timeout is 60 seconds. External senders must supply stable idempotency identities. DBOS message durability does not make a shell command, Git push, or WebSocket receipt exactly once. [Communication guarantees](https://docs.dbos.dev/typescript/tutorials/workflow-communication)

### Interpreter and recovery decisions

DBOS workflow functions must call recorded operations in a deterministic order. Put database access, wall-clock reads, UUID generation, and external operations inside registered durable operations or `DBOS.runStep`. [Workflow determinism](https://docs.dbos.dev/typescript/tutorials/workflow-tutorial)

Factory design:

- One interpreter owns progression. HTTP handlers persist commands/facts and send their identities; they never choose the next activity.
- Freeze the definition before enqueueing. Persist command intent before socket delivery and correlate command, execution, harness turn, and recovery attempt separately.
- Replaying an already-recorded operation must return the same persisted command identity. Daemon duplicate detection and result reconciliation remain necessary after an interrupted external operation.
- Human waits hold durable interaction state and no active harness execution permit. Queue concurrency for whole workflows must not become a harness-slot limit.
- Cancellation is first a Factory command so active work receives cancellation and retained documents/worktrees remain inspectable.

DBOS recovers only workflows with the matching application version. In 4.27.6, startup also selects the configured executor identity; the default local identity is `local`. Keep a stable single-coordinator identity and enforce a singleton deployment. `DBOS.setConfig` supports explicit `applicationVersion`, `executorID`, `systemDatabaseUrl`, and a caller-owned Postgres pool. [Configuration](https://docs.dbos.dev/typescript/reference/configuration), [4.27.6 source archive](https://registry.npmjs.org/@dbos-inc/dbos-sdk/-/dbos-sdk-4.27.6.tgz)

Changing the sequence of durable operations can invalidate replay. DBOS documents patching and coexisting versions, but this product explicitly chooses draining: reject incompatible coordinator startup while affected nonterminal runs exist; require them to finish or be explicitly cancelled first. Changing only the application version otherwise strands old runs. Do not deploy parallel legacy interpreters. [Upgrade semantics](https://docs.dbos.dev/typescript/tutorials/upgrading-workflows)

## Codex app-server adapter

The app server uses bidirectional JSONL over stdio. Initialize before other requests, then send `initialized`. Discover models with `model/list`; each entry supplies supported effort options. `turn/start` accepts explicit model, effort, working directory, and an output JSON Schema. `outputSchema` applies only to that turn. Tool approvals and user questions arrive as server requests, while progress/completion arrive as notifications. Experimental interactions require the initialization capability opt-in. [Official OpenAI App Server documentation](https://learn.chatgpt.com/docs/app-server)

### Facts from the generated 0.154.0 protocol

These are observations of the pinned local binary, generated without running a model:

- `InitializeCapabilities` includes `experimentalApi` and `requestAttestation`.
- `thread/start` creates a conversation; `thread/read` and `thread/resume` support persisted history and continuation.
- `turn/start` uses `threadId`, `input`, `cwd`, `model`, `effort`, and `outputSchema`. `turn/interrupt` requires the active `threadId` and `turnId`.
- `item/tool/requestUserInput` has `threadId`, `turnId`, `itemId`, questions, and `isBlocking`. The generated schema marks `autoResolutionMs` deprecated. An answer has shape `{ answers: { questionId: { answers: ["answer"] } } }`.
- Permission request methods include `item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, and `item/permissions/requestApproval`; those decisions must remain separate from workflow handoff approval.
- `turn/completed` contains a turn with status, items, and error. A completed turn alone is insufficient to advance a workflow: validate the named outcome and declared document outputs.

A real read-only stdio smoke test succeeded with this binary: initialize, initialized, model/list, terminate. It returned `gpt-6-astra`, `gpt-5.6-sol`, and `gpt-5.6-terra` with efforts low through ultra; `gpt-5.6-luna` through max; and `gpt-5.5` through xhigh. No model turn or repository mutation was performed. Treat this as local discovery evidence, not a permanent global model list.

During implementation, the daemon adapter also passed an isolated real model smoke test with Codex 0.154.0, `gpt-5.6-luna`, low effort, and a temporary empty working directory. With no kickoff prompt it returned a structured requirements question. A separate app-server process resumed the persisted session, accepted the user's answer, and completed with an acceptance-criteria document in the same session. This establishes the selected CLI's basic cross-process conversation recovery and structured output behavior; it does not establish full socket/coordinator recovery or publication acceptance.

Factory design: use a fresh Codex conversation per activity execution, keep questions/answers within that execution, and persist the session and turn identities in the daemon journal before acknowledging them. An app-server transport disappearance is not proof that execution failed. Reconcile stored session/worktree evidence; ask Retry or Cancel when its outcome remains ambiguous. Prompt-free requirements should explicitly initiate the interview. Required human input policy must be enforced by durable interaction state rather than trusting prose instructions alone.

ADR-0013's stdin rule applied to one-shot `codex exec`: stdio app-server intentionally keeps stdin open for protocol traffic. Update that architectural rule when replacing the adapter.

## Worktrees and publication

`git worktree add -b <branch> <path> <commit>` creates a new branch and checkout at an explicit commit; linked worktrees share repository objects while maintaining separate working directories and indexes. [Git worktree](https://git-scm.com/docs/git-worktree)

Factory design: resolve the selected local branch to a commit before creation, default to the current branch, and retain both pinned commit and branch name. Place document materializations and setup logs outside the tracked checkout. Never copy uncommitted files or environment files from the original checkout. Keep a per-run branch/path and retain it after terminal states.

`gh pr create` supports explicit repository, head, base, title, body file, and draft mode. Explicit `--head` prevents its implicit push/fork behavior. Its `--dry-run` can still push, so do not use it as a harmless preview. Success prints the PR URL. [PR creation](https://cli.github.com/manual/gh_pr_create)

`gh pr list --repo <repository> --head <branch> --base <base> --state all --json ...` can return ID, number, URL, head/base refs, head commit, owner, repository, and state. `--head` filtering does not accept owner-prefixed syntax. Check returned repository identity as well as branch name. [PR lookup](https://cli.github.com/manual/gh_pr_list)

Factory design:

1. Resolve and persist repository, push remote, base, run branch, reviewed tree, title/body/draft and publication intent before external operations.
2. Commit with normal hooks. Recompute the committed tree and worktree state after hooks; any content change invalidates review/publication approval.
3. Use an ordinary non-forced push with an explicit source and destination. A non-fast-forward rejection is a recoverable decision, never permission to force. [Git push semantics](https://git-scm.com/docs/git-push)
4. After interruption, inspect the remote branch and query matching PRs before recreating anything. Persist discovered PR identity and URL. An uncertain or multiple match requires recovery, not another blind create.

## Closed-portal browser notifications

The Push API delivers to an origin's service worker even when no application page is open; it can start the worker when needed. It requires a secure context. Subscription replacement and deactivation are part of the lifecycle. Browser/OS availability still constrains delivery. [W3C Push API working draft](https://www.w3.org/TR/push-api/)

Request notification permission from an explicit user gesture and expose granted, denied, and undecided enrollment states. [Permission API](https://developer.mozilla.org/en-US/docs/Web/API/Notification/requestPermission_static)

Use Node `web-push` with stable environment-provided VAPID credentials. Its subscription shape contains endpoint and `p256dh`/`auth` keys; its browser counterpart subscribes with the public VAPID key and `userVisibleOnly: true`. Delivery responses expose status code, headers, and body. [Node Web Push](https://github.com/web-push-libs/web-push)

The service worker handles `push` with `event.waitUntil(registration.showNotification(...))`. Handle notification clicks by closing the notification, matching/focusing the correct run window, or opening that run URL. [Push event](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/push_event), [Notification clicks](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/notificationclick_event)

Push-service acceptance is not proof the browser displayed a message. Persist that distinction in delivery status. [RFC 8030 section 5](https://www.rfc-editor.org/rfc/rfc8030.html#section-5)

Factory design: persist a browser recipient independently of its replaceable subscription; protect management and run binding using a browser-specific management token. Persist notifications before attempts, reuse notification IDs as browser tags, deactivate expired subscriptions, and record push failures independently of activity/PR completion. Do not put management tokens in notification URLs or payloads. Acceptance requires a real subscribed desktop browser, all portal tabs closed, correct-run opening on click, and a second browser proving recipient separation. Mocks cannot establish that acceptance result.
