# Durable execution substrate comparison

Date: 2026-09-12 · Decision: [#7](https://github.com/09millarda/agents-assemble/issues/7)

## Recommendation and evidence boundary

**Select an Execution-owned PostgreSQL state machine with TypeScript workers as the architectural baseline, supported by the accompanying [bounded crash experiment](durable-execution-conformance.md) and [ADR 0003](../architecture/0003-durable-execution-and-recovery.md).** It directly accommodates the existing requirement that assignment fencing, transition acceptance, counters and the Execution outbox commit together. Temporal is a credible later adapter, especially if operational evidence justifies its timer and workflow tooling; the investigated declarative reference runtime is not yet a demonstrated durable fit. This is an engineering recommendation from the comparison below, not a performance benchmark or certification.

The constraints are the project's [context ownership rules](../../CONTEXT.md#data-and-event-rules) and [amended playbook contract](../architecture/0002-playbook-and-action-contract.md#conformance-amendments-from-6). All candidates must retain immutable manifests, separate occurrence/attempt/effect identities, accepted human receipts, independent recovery obligations, persisted grants and explicit successor admission. A framework's task completion cannot substitute for those domain decisions. [ADR 0002](../architecture/0002-playbook-and-action-contract.md#durable-execution-retries-and-cancellation)

This note is a primary-source/documentation investigation. PostgreSQL references use major 17 to match the PostgreSQL 17.9 experiment; upstream Java and TypeScript SDK citations pin the inspected source commits, not promised release compatibility. No Temporal or Open Workflow runtime was installed or fault-tested here; no production dependency versions or licensing compatibility are selected. [License/parity decision #5](https://github.com/09millarda/agents-assemble/issues/5) remains independent.

## Verified substrate facts

| Candidate | Facts established by official documentation/source | What those facts do not establish |
| --- | --- | --- |
| PostgreSQL with application-owned workers | WAL supports crash recovery of committed database changes. Row locks and `SKIP LOCKED` support competing consumers of queue-like tables; PostgreSQL explicitly warns that skipping locked rows gives an inconsistent view. Serializable transactions can abort and require whole-transaction retries. [WAL](https://www.postgresql.org/docs/17/wal-intro.html), [locking](https://www.postgresql.org/docs/17/sql-select.html#SQL-FOR-UPDATE-SHARE), [isolation](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-SERIALIZABLE) | Database primitives do not themselves provide the playbook interpreter, durable timer dispatcher, fair scheduling, message protocol or external-effect reconciliation. Those are proposed application responsibilities, requiring tests. |
| Temporal behind an Execution port | TypeScript Workflows run deterministic logic in a sandbox; external I/O belongs in Activities and Activity results enter history. Timers survive Worker/Service downtime and resolve after they return. [Workflow basics](https://docs.temporal.io/develop/typescript/workflows/basics#develop-workflow-logic), [durable timers](https://docs.temporal.io/develop/typescript/workflows/timers#what-is-a-timer) | A replayable Workflow does not prove our receipt validation, assignment fencing or database/outbox atomicity. Activities execute in workers; their results are reported afterward, and Temporal recommends idempotent Activities. An external success before its recorded result remains a boundary the application must handle. [Activities](https://docs.temporal.io/activities) |
| Open Workflow Java reference implementation | The project formerly called CNCF Serverless Workflow is now Open Workflow. Its Java reference runtime executes JSON/YAML and includes `Do`, `Switch`, `Fork`, `For`, `Wait`, calls and retries; its assembled Jackson module uses JQ expressions. It requires Java 17+. The TypeScript SDK documents definition parsing, building and validation, not a durable worker engine. [Rename](https://github.com/serverlessworkflow), [Java runtime](https://github.com/open-workflow-specification/sdk-java/blob/dff82db0e022d118ff5e79aa71c78865016cc6a3/impl/README.md), [TS SDK](https://github.com/open-workflow-specification/sdk-typescript/blob/122bb442a0880ce10e28c4d7c5902880846ebba5/README.md) | Similar control-flow names do not establish compatibility with our JSON Pointer bindings, restricted condition AST, snapshot membership, finite grants, exact approvals or successor delivery mapping. A translation/customization layer needs its own conformance evidence. [Our grammar](../architecture/0002-playbook-and-action-contract.md#portable-grammar-and-authoring) |

The Java runtime's persistence documentation says lifecycle events record progress, the application must restart instances no longer owned by another JVM, H2 MVStore is the concrete store, and relational/PostgreSQL persistence is future work. Its inspected `WaitExecutor` uses `CompletableFuture.delayedExecutor` with the resolved duration. These sources do **not** prove preserved absolute wait deadlines, multi-worker fencing, or atomic state plus our outbox after a crash. This rejects the inspected runtime as a proven drop-in candidate; it is not a claim that all Open Workflow implementations lack durability. [Pinned persistence README](https://github.com/open-workflow-specification/sdk-java/blob/dff82db0e022d118ff5e79aa71c78865016cc6a3/impl/persistence/README.md#L5), [pinned wait executor](https://github.com/open-workflow-specification/sdk-java/blob/dff82db0e022d118ff5e79aa71c78865016cc6a3/impl/core/src/main/java/io/serverlessworkflow/impl/executors/WaitExecutor.java#L57)

Temporal defaults require deliberate adaptation: Activities retry automatically with unlimited attempts; `maximumAttempts: 1` means one attempt, while zero means unlimited. Start with retries disabled for unsafe domain invocations, then use explicit safe retry classes and grant accounting. Heartbeat timeout can trigger another Activity attempt; cancellation delivery depends on heartbeats and Activity cooperation. Neither timeout nor cancellation notification proves a lost runner stopped publishing. Interpreter upgrades also require replay-compatible patching or versioned Workers. [Retry policy](https://docs.temporal.io/encyclopedia/retry-policies#maximum-attempts), [heartbeats/cancellation](https://docs.temporal.io/develop/typescript/activities/timeouts#heartbeat-an-activity), [versioning](https://docs.temporal.io/develop/typescript/workflows/versioning)

## Contract fit and ownership recommendation

The following is a proposed design derived from [CONTEXT.md](../../CONTEXT.md#data-and-event-rules) and [ADR 0002](../architecture/0002-playbook-and-action-contract.md#durable-execution-retries-and-cancellation), not a guarantee supplied by any candidate:

1. **One canonical acceptance point.** Lock/version-check an Execution aggregate, check authoritative assignment generation and lease, validate the incoming command, charge any new invocation, update progress/recovery/timer state and append the Execution outbox in one Execution transaction. Persist accepted fan-out membership and branch choices; retries never re-expand them. Use short claim/commit transactions, not locks held across runner or provider calls.
2. **Each participant owns its transaction.** Human Interaction accepts an authorized version-bound reply into its records and outbox. Execution separately records inbox acceptance and the effect-authorizing canonical receipt. Human acceptance is not yet Execution acceptance: the UI must distinguish delivery pending, accepted and rejected/stale. Knowledge, Fleet and Integrations follow the same local inbox/state/outbox pattern; no transaction writes two contexts.
3. **Duplicates and ordering are domain inputs.** Deduplicate by scoped stable message/operation ID and stored payload digest; mismatching payloads conflict. Retain source aggregate versions and reconcile gaps; ignore stale observations without clearing a newer proposal. Commit inbox and local consequences together. Publish outbox messages at least once and mark delivery separately; a crash after publication can cause duplicates, never a second authorized effect solely because delivery repeated.
4. **Persist time and allowances.** Store absolute wait/backoff deadlines, budget consumption, attempt limits and scheduler claim generations. A restart scans eligible work and rechecks state before dispatch. A timer expiry expires/escalates a request; it supplies no approval. A lease generation fences acceptance, while effecting adapters separately enforce scoped grants and their effect protocol.
5. **Preserve uncertainty.** Integrations persist effect identity, payload and external-resource mapping before attempting publication. If success precedes a durable receipt, reconcile through provider idempotency or lookup; otherwise require recovery. Keep unknown publication, workspace uncertainty, pending cancellation and event gaps independently visible. Retain/adopt does not clear them or renew budgets; a successor needs fresh admission and inherited delivery mapping.

For Temporal, the safest fit with these existing invariants keeps the database canonical and treats Workflow wakeups/Activities as idempotent proposals to Execution. An outbox bridges database commit to Temporal notification; receiving a notification is not authority to dispatch. Alternatively making Temporal history canonical would require a new design for atomic transition/fence/outbox acceptance rather than assuming a transaction spans Temporal and application PostgreSQL. This is an inference from Temporal's separate [Workflow/Activity boundary](https://docs.temporal.io/develop/typescript/workflows/basics#develop-workflow-logic) and our [local transaction constraint](../../CONTEXT.md#data-and-event-rules), not a documented Temporal incompatibility.

## Deployment implications

| Mode | PostgreSQL/state-machine proposal | Temporal option | Inspected declarative option |
| --- | --- | --- | --- |
| Hosted | Application workers plus the PostgreSQL already in the deployment sketch; team owns scheduling/recovery operations. | Operate or procure a Temporal Service alongside application data/workers. | Add Java execution and its persistence/restart ownership integration. |
| Self-hosted | Same core and database protocol; operator owns backup, migrations and worker health. | Service deployment, security, visibility and schema upgrades add operator responsibilities. | Package Java plus the chosen state store and prove unattended recovery. |
| Personal machine | Same PostgreSQL baseline can run locally; packaging and suspend/resume behavior remain to validate. | Single-binary development server exists, but official docs position it for development/testing; do not treat it as the proven durable personal production package. | Java/MVStore suggests a small local topology, but footprint and production restart behavior were not measured. |

These are engineering implications of the [project deployment sketch](../../CONTEXT.md#portable-deployment-sketch), [Temporal deployment guide](https://docs.temporal.io/self-hosted-guide/deployment), [Temporal operational guide](https://docs.temporal.io/self-hosted-guide), and the [Java persistence model](https://github.com/open-workflow-specification/sdk-java/blob/dff82db0e022d118ff5e79aa71c78865016cc6a3/impl/persistence/README.md). No cost, resource-footprint, throughput, HA, backup/restore, OS packaging or license claim was tested.

Reconsider Temporal if representative load or recovery drills show sustained due-work lateness beyond the agreed scheduling objective, growing outbox age that misses the recovery objective, persistent lock/serialization contention after ordinary tuning, or history retention/migration work beyond the accepted operational budget. Set those objectives from release requirements and measure them before declaring a threshold exceeded; this investigation supplies no justified numeric capacity ceiling. Reconsider a declarative runtime only after its exact version and adapter pass our crash/contract traces. Neither move requires changing the portable playbook document merely to expose vendor APIs.
