# Portable package envelope: primary-source findings

Date: 2026-09-12 · Decision: [#17](https://github.com/09millarda/agents-assemble/issues/17)

This note supplies research for the disposable envelope investigation. Recommendations below are engineering choices, not production conformance or publisher-identity certification. [ADR 0010](../architecture/0010-portable-community-publication.md) requires complete offline closures, approved provenance, immutable identity and separate execution grants; [ADR 0011](../architecture/0011-open-source-licensing-and-edition-parity.md) requires preserved component terms and recorded redistribution permission. Neither a successful hash check nor this experiment applies a software license.

## Recommendation

Use a versioned, deliberately narrow ZIP_STORED envelope containing canonical JSON metadata and content-addressed binary objects. Verify without extracting author-selected paths. Bind component identities, dependency digests, logical resource paths, rights/notice records and approved provenance into the hashed metadata. Keep archive transport hashing separate from content and closure identity. Treat all claims as unverified unless local policy already pins an authorized issuer key. These choices implement the boundaries in [ADR 0010, Package identity and portable content](../architecture/0010-portable-community-publication.md#package-identity-and-portable-content).

## Verified facts and their implications

| Choice | Verified fact | Engineering assessment |
| --- | --- | --- |
| ZIP_STORED | ZIP has corresponding local/central headers, optional data descriptors and ZIP64 fields. Method zero stores bytes without compression. [PKWARE APPNOTE, §§4.3, 4.4.5](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT) | A strict subset avoids decompression and makes byte extents directly checkable; duplicate metadata still needs validation. |
| tar | Python documents repeated names overwriting earlier entries and warns that even its data filter does not prevent denial of service. [Python tarfile, verification guidance](https://docs.python.org/3/library/tarfile.html#hints-for-further-verification) | A similarly strict regular-file tar profile is viable, but supplies no compelling benefit for this small random-access envelope. Do not equate extraction filters with complete validation. |
| JSON/base64 | Base64 encodes three input octets as four characters, with padding rules; its specification distinguishes canonical padding and rejection of non-alphabet input. [RFC 4648, §§3–4](https://www.rfc-editor.org/rfc/rfc4648#section-3) | One container syntax is attractive, but binary payloads grow approximately one third before outer compression and create additional decoding/allocation work. Prefer separate raw objects. |

JCS forbids duplicate object names, preserves Unicode strings without normalization, rejects lone surrogates and nonfinite numbers, serializes numbers using ECMAScript rules, sorts names by UTF-16 code units, preserves array order, and emits UTF-8 without inter-token whitespace. A generic sorted JSON serializer is therefore insufficient for unrestricted JCS. [RFC 8785, §§3.1–3.2](https://www.rfc-editor.org/rfc/rfc8785#section-3.1)

**Recommended canonical profile:** restrict metadata object keys to ASCII and numeric values to integers within ±(2^53−1); represent exact decimals as schema-defined strings where needed. Preserve unrestricted valid Unicode string values. Reject unsupported numbers and keys rather than silently translating them. Require incoming metadata bytes to equal the canonical serialization exactly, including no BOM or trailing newline. These are narrower product choices; they are not additional RFC requirements. Keep opaque resource bytes byte-exact. [JCS input and serialization requirements](https://www.rfc-editor.org/rfc/rfc8785#section-3.2)

Python's JSON decoder accepts repeated names by retaining the last value and accepts nonfinite constants by default. `object_pairs_hook` exposes the original pairs; `parse_float`, `parse_int` and `parse_constant` allow explicit rejection. Decode strict UTF-8 before JSON parsing because the bytes API also accepts UTF-16/32. Bound input before parsing. [Python 3.14 JSON API and compliance](https://docs.python.org/3.14/library/json.html#standard-compliance-and-interoperability)

## Parser requirements to exercise

The following are proposed profile checks, motivated by the archive mechanisms above and the bounded rejection requirement in [#17](https://github.com/09millarda/agents-assemble/issues/17):

1. Accept only fixed metadata filenames and `blobs/<lowercase-sha256>` member names. Reject duplicate names before any dictionary conversion or name lookup. The manifest must inventory exactly the accepted object set, including declared sizes and computed digests; neither missing nor extra objects pass.
2. Parse every physical record boundary. Compare local and central filenames, method, flags, CRC and sizes; verify in-bounds, non-overlapping extents with no hidden gaps. Reject prepended/appended data, contradictory counts/offsets, encryption, split archives, ZIP64, descriptors, extras, comments, unknown flags, directory/link/device attributes and unsupported versions. This is intentionally stricter than general ZIP. [PKWARE APPNOTE, §§4.3.7–4.3.16 and 4.4](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT)
3. Do not use `extractall` to create the Catalog state. Python supports archives with duplicate filenames, and extraction normalizes some unsafe names. Such normalization can change the identity being validated. Read validated members by their enumerated entry, then store under locally generated digest paths. [Python ZIP member and extraction APIs](https://docs.python.org/3.14/library/zipfile.html#zipfile.ZipFile.open)
4. Validate logical resource paths separately: reject absolute paths, parent segments, backslashes, NUL/control characters and case-fold collisions. Keep the supported path alphabet explicit. Repeated references to one blob may be legitimate; duplicate logical paths are not. [Python archive verification guidance](https://docs.python.org/3/library/tarfile.html#hints-for-further-verification)
5. Cap total transport bytes before loading, then member count, per-member bytes, aggregate payload, metadata bytes, JSON depth/nodes/string length, component count, dependency edges and graph depth. Reject limits before corresponding allocation/traversal, including deeply nested JSON before recursive decoding. Use an isolated temporary staging directory and no-follow locally generated paths; a failed attempt must expose no partially registered release. [Python JSON resource warning](https://docs.python.org/3.14/library/json.html), [Python archive resource guidance](https://docs.python.org/3/library/tarfile.html#hints-for-further-verification)

**Limit selection:** standards do not establish this product's correct capacities. Choose finite conservative experiment values, execute boundary and just-over-boundary cases, and record them as the format's initial acceptance profile rather than benchmark-derived capacity. Large legitimate packages need an explicit later profile/version decision. SHA checks must accompany CRC checks; passing CRC is not the required content identity. [#17 acceptance scope](https://github.com/09millarda/agents-assemble/issues/17), [ADR 0010 identity contract](../architecture/0010-portable-community-publication.md#package-identity-and-portable-content)

## Offline trust

Ed25519 defines signature verification for a given public key and message, with 32-byte public keys and 64-byte signatures; it does not establish which organization owns the supplied key. [RFC 8032, §§5.1.7 and 7.1](https://www.rfc-editor.org/rfc/rfc8032#section-5.1.7) TUF separately bootstraps trusted roots through an out-of-band process and uses additional metadata for freshness/rollback protections. [TUF, §§2.1 and 5.2](https://theupdateframework.github.io/specification/latest/#load-trusted-root-metadata)

**Recommended minimum:** an optional detached Ed25519 attestation signs a domain-separated canonical statement binding format, issuer/organization, package/version and content/closure digests. A locally provisioned trust record maps the key to its permitted issuer/organization scope. An embedded public key, URL or matching digest cannot create that record. Reject invalid signatures under recognized keys; preserve unsigned/unknown-key claims as unverified if local import policy permits. Verifying a root attestation must not imply every dependency publisher was independently authenticated. Preserve per-component evidence for advisory matching. These are product trust choices implementing [ADR 0010](../architecture/0010-portable-community-publication.md#package-identity-and-portable-content), not a claim of TUF implementation.

Pinning permits offline verification against locally known keys; it does not establish current upstream revocation, delegation or advisory state. Key rotation/revocation distribution, publisher onboarding and federation remain subsequent work. Imported signatures confer no permission to execute or redistribute; local rights policy and runtime grants remain independent. [ADR 0010, Import, fork and update](../architecture/0010-portable-community-publication.md#import-fork-and-update), [TUF trust/freshness model](https://theupdateframework.github.io/specification/latest/#roles)

## Local API probes

On Python 3.14.4, minimal standard-library probes confirmed the documented traps: parsing `{"key":1,"key":2}` returned `{'key': 2}`; parsing `NaN` returned `nan`. A ZIP with two `same` members listed both entries, while reading by name returned the second payload. Reading each enumerated entry recovered both distinct payloads. These are observations of default APIs, not the retained envelope prototype's acceptance results. The relevant Python documentation is the 3.14 family; the project has no production dependency/version commitment from this note. [JSON defaults](https://docs.python.org/3.14/library/json.html#standard-compliance-and-interoperability), [ZIP duplicate entries](https://docs.python.org/3.14/library/zipfile.html#zipfile.ZipFile.open)
