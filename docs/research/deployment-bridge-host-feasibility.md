Candidate: one shared-tenancy Linux `t3.micro` in `eu-west-1`, explicitly `standard` CPU credits at launch, one 8 GiB gp3 root volume at baseline performance, one public IPv4, a proposed two-hour compute window. The arithmetic below assumes all host storage is also released after two hours; unresolved recovery may require longer retention.

Compute and gp3 were read directly from the [official AWS regional EC2 price CSV, version 20260910195514](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonEC2/20260910195514/eu-west-1/index.csv), published 2026-09-10, rate effective date 2026-09-01. Matching SKUs: compute `DXH6X4VVFUT4EUU5` (Linux, shared, no preinstalled software, `EU-BoxUsage:t3.micro`) and gp3 `TXACT7E3PV6ZX2NM` (`EU-EBS:VolumeUsage.gp3`). IPv4 is charged for both in-use and idle addresses. [VPC pricing](https://aws.amazon.com/vpc/pricing/).

Linux compute and gp3 are billed by the second with a 60-second minimum; the storage estimate follows AWS's 30-day-month prorating example. gp3 includes 3,000 IOPS and 125 MB/s baseline throughput. Extra provisioned performance is outside this estimate. Storage is charged until released, so stopping the instance is insufficient cleanup. [EC2 On-Demand pricing](https://aws.amazon.com/ec2/pricing/on-demand/), [EBS pricing](https://aws.amazon.com/ebs/pricing/).

This is a baseline host subtotal, **not a hard spending cap or the full deployment experiment's cost**. It excludes taxes, data transfer, retained storage/snapshots, CloudWatch/S3 logging, Lambda or other deployment targets, and any optional networking or KMS resources. The two-hour limit requires an implemented stop/teardown mechanism and verification. Stop new admissions and preserve/export recovery state before deletion. If an operation remains unresolved, stop compute and retain its recovery volume or a verified restorable export; do not erase the only authoritative ledger to meet a timer. Retention then increases the baseline estimate. After effects are accounted and evidence retained, terminate with root-volume deletion and verify that no fixture volumes or allocated addresses remain. Session Manager and Run Command have no additional usage charge for EC2 instances; other Systems Manager features or associated services can charge separately. [Systems Manager pricing](https://aws.amazon.com/systems-manager/pricing/).

## Feasibility and prerequisites

- **CPU and memory:** the price record identifies t3.micro as 2 vCPU / 1 GiB RAM. A small PostgreSQL database and a few Node processes are a plausible experiment configuration, not a measured capacity result. Explicit Standard mode avoids paid surplus CPU credits; T3 normally defaults to Unlimited and receives no launch credits. A fresh Standard host can therefore initialize slowly. Keep setup lightweight and measure memory/startup time before relying on a two-hour test window. [Launch configuration](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-launch-parameters.html), [Standard credit behavior](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/burstable-performance-instances-standard-mode-concepts.html).
- **AMI/storage:** use an x86_64 Linux AMI compatible with t3.micro. Verify its root snapshot accepts an 8 GiB volume; EBS block-device size cannot be smaller than its source snapshot. Also verify free-tier eligibility if relying on that benefit. [EBS block-device API](https://docs.aws.amazon.com/AWSEC2/latest/APIReference/API_EbsBlockDevice.html).
- **Free plan:** AWS lists t3.micro and gp3 as eligible under its post-2025-07-15 program, but benefit duration and credits depend on the account. The newer program lasts six months or until credits are exhausted; older accounts follow different limits. Eligibility does not establish a zero bill. Actual account plan, remaining credits, EC2 quota, effective SCP/IAM launch permissions and AZ capacity were not established by this research. [EC2 Free Tier rules](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-free-tier-usage.html).
- **Network:** the direct-public-host design needs a subnet with an internet-gateway route, assigned public IPv4, working DNS and suitable outbound rules. Default VPCs normally provide public subnets and an internet gateway, but their configuration can be changed or deleted. Use a dedicated security group allowing only the required HTTPS ingress; no inbound SSH or PostgreSQL is needed. This design does not require a NAT gateway or load balancer. [Default VPC components](https://docs.aws.amazon.com/vpc/latest/userguide/default-vpc-components.html), [internet gateway prerequisites](https://docs.aws.amazon.com/vpc/latest/userguide/VPC_Internet_Gateway.html).
- **SSM:** the AMI needs a supported installed/running SSM Agent and appropriate instance permissions; administration requires outbound HTTPS to regional SSM endpoints. SSM establishes its connections without inbound SSH. The administrator remains a trusted host operator (the default session user is administrative). [Session Manager prerequisites](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-prerequisites.html), [Session Manager overview](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager.html).
- **HTTPS trust:** generate the private key on the host and distribute only its public certificate through an authenticated administration path. Pin that certificate in the trusted GitHub caller and preserve certificate/server-name verification; the certificate must match the chosen URL host. curl supports a supplied trust file with `--cacert`. Fetching a certificate from an unauthenticated endpoint is not authenticated pin bootstrap. This permits a disposable endpoint without a purchased domain or managed TLS termination, but remains an implementation recommendation to test. [curl TLS verification](https://curl.se/docs/sslcerts.html).
- **Credential boundary:** separate Unix users/processes alone do not restrict the instance profile. AWS documents local firewall rules that limit metadata access by user, including IMDSv2 requests. If only Integrations should reach AWS credentials, implement and test that restriction while preserving SSM access; host root remains trusted. IMDSv2 by itself does not establish process isolation. Execution should still expose only its claim contract and database grants, not give Integrations direct approval-table ownership. [AWS IMDS process-access controls](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instance-metadata-limiting-access.html).
