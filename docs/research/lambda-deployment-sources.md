# Lambda deployment provider evidence

Research date: 2026-09-12. Supports decision [#15](https://github.com/09millarda/agents-assemble/issues/15). This is documentation research and experiment design; no GitHub workflow or AWS mutation was executed. Provider capabilities below were checked against current primary sources, not installed SDK behavior.

## Summary and recommendation

**Recommendation:** use GitHub Actions as the trusted deployment executor, with AWS OIDC, packaged release artifacts, explicit CloudFormation change sets, and SAM/CodeDeploy traffic shifting. Keep the product's deployment intent and operation identity durable outside an individual runner. Treat uncertain dispatch or execution outcomes as reconciliation states. The APIs supply useful identifiers and retry guards, but the cited interfaces do not establish a cross-provider exactly-once transaction.

## Verified facts

### Dispatch, discovery, and workflow identity

- `POST /repos/{owner}/{repo}/actions/workflows/{workflow_id}/dispatches` accepts a workflow ID or filename, a branch/tag `ref`, and declared inputs. Fine-grained tokens require repository Actions write permission. The API-version-qualified 2022-11-28 reference documents `return_run_details: true`, returning HTTP 200 with `workflow_run_id`, `run_url`, and `html_url`; false returns 204. The unqualified current reference shows 200 without that parameter. Neither schema lists a dispatch idempotency key. [Version-qualified dispatch reference](https://docs.github.com/en/rest/actions/workflows?apiVersion=2022-11-28#create-a-workflow-dispatch-event), [current dispatch reference](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event).
- GitHub announced optional dispatch run details on 2026-02-19; `gh workflow run` support begins with CLI 2.87.0. A design assuming that every dispatch necessarily returns only 204 is outdated. [GitHub changelog](https://github.blog/changelog/2026-02-19-workflow-dispatch-api-now-returns-run-ids/).
- Workflow run listing supports filters including workflow, event, creation time, and head SHA; filtered searches can return at most 1,000 results. Run objects expose ID, workflow ID, head SHA, path, display title, status, conclusion, and run attempt. The documented listing parameters do not include arbitrary dispatch inputs or a client operation ID. Individual runs can be queried by run ID. [Workflow runs REST API](https://docs.github.com/en/rest/actions/workflow-runs).
- `run-name` can interpolate `inputs`, providing a provider-visible correlation label. This is a configurable label, not an API uniqueness guarantee. [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#run-name).
- For `workflow_dispatch`, `GITHUB_SHA` is the last commit on the dispatched branch/tag and the workflow must exist on the default branch to trigger. The documented dispatch `ref` contract is branch/tag, so raw commit-SHA dispatch support should not be assumed. [Dispatch event semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch).
- GitHub recommends full commit-SHA pinning of third-party actions and reusable workflows; a tag can move. [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use#using-third-party-actions).

### Environment gates, OIDC, and concurrency

- Environment rules gate jobs referencing that environment. Only one configured required reviewer must approve; preventing self-review is optional. Administrators can bypass protection rules by default unless disabled. Branch/tag rules match the workflow's `GITHUB_REF`; “protected branches only” allows all branches when no branch protection rules exist. Required reviewers on Free/Pro/Team are limited to public repositories. [Environment protection reference](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).
- AWS authentication can exchange GitHub OIDC tokens for temporary credentials; trust policies should constrain audience and subject. Environment jobs use an environment subject context instead of the branch context. AWS does not support arbitrary GitHub custom claims as separate trust-policy claims. [GitHub AWS OIDC guide](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws).
- Current GitHub docs say repositories created after July 15, 2026 use immutable owner/repository IDs in default OIDC subjects; earlier repositories retain the previous format unless opted in, renamed, or transferred. Subject customization can include reusable workflow identity. Therefore an old name-only example must not be copied without checking this repository's actual subject format. [OIDC reference](https://docs.github.com/en/actions/reference/security/oidc#immutable-subject-claims).
- STS `AssumeRoleWithWebIdentity` defaults to a one-hour session, accepts 900 seconds through the role's maximum duration, and intersects session-policy permissions with role permissions. This lifetime is an AWS credential lifetime, not the application's deployment-approval expiry. [STS API](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRoleWithWebIdentity.html).
- Concurrency groups allow one running job/run. Default `queue: single` replaces an existing pending entry; current `queue: max` permits up to 100 pending entries and cancels overflow. `queue: max` cannot be combined with `cancel-in-progress: true`. Groups are case-insensitive and scoped to the repository. FIFO follows entry into concurrency waiting, not dispatch order. [Concurrency documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).

### Packaged artifact and CloudFormation operations

- `sam package` uploads code/dependencies and emits a template whose local artifact references become S3 locations. `sam deploy` can package implicitly, so invoking it on source is not proof of promoting previously tested bytes. [SAM package reference](https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/sam-cli-command-reference-sam-package.html).
- SAM `CodeUri` supports a `FunctionCode` object containing `Bucket`, `Key`, and `Version`; `Version` maps to CloudFormation `S3ObjectVersion`. The bucket must be in the function's AWS Region. [FunctionCode reference](https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/sam-property-function-functioncode.html).
- SAM `AutoPublishAlias` generates a Lambda version and alias; `AutoPublishCodeSha256` controls version-publication detection in conjunction with `CodeUri`. It is not documented as a replacement for immutable object selection or a byte-verification gate. [SAM function reference](https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/sam-resource-function.html).
- `CreateChangeSet` takes a unique stack-local `ChangeSetName` and optional `ClientToken` specifically for retrying the same create request. Creating a `CREATE` change set allocates a stack ID in `REVIEW_IN_PROGRESS` without creating template resources. [CreateChangeSet](https://docs.aws.amazon.com/AWSCloudFormation/latest/APIReference/API_CreateChangeSet.html).
- `DescribeChangeSet` accepts a change-set name/ARN and returns status, execution status, parameters, and changes. `AVAILABLE` means executable; `OBSOLETE` can mean the stack was already updated. Creating a change set and successfully executing its resources are separate states. [DescribeChangeSet](https://docs.aws.amazon.com/AWSCloudFormation/latest/APIReference/API_DescribeChangeSet.html).
- `ExecuteChangeSet` accepts the exact name/ARN and `ClientRequestToken` for retries. A successful call starts a stack update; callers must query stack status. Executing a change set deletes other change sets for that stack. [ExecuteChangeSet](https://docs.aws.amazon.com/AWSCloudFormation/latest/APIReference/API_ExecuteChangeSet.html).
- Stack events expose `ClientRequestToken`; events generated by one operation share it. This supports correlating stack effects even when a runner loses the execute response. [StackEvent](https://docs.aws.amazon.com/AWSCloudFormation/latest/APIReference/API_StackEvent.html).

### Versions, health, and rollback

- Published numbered Lambda versions preserve function code and most configuration; `$LATEST` remains mutable. Versioning is not a promise that every external dependency or managed runtime characteristic is frozen. [Lambda versions](https://docs.aws.amazon.com/lambda/latest/dg/configuration-versions.html).
- `PublishVersion` can require both `CodeSha256` and function `RevisionId` to match, protecting against code/configuration changing between upload and publish. [PublishVersion](https://docs.aws.amazon.com/lambda/latest/api/API_PublishVersion.html).
- `UpdateAlias` optionally requires the alias's `RevisionId`; a mismatch returns 412 `PreconditionFailedException`. Responses contain alias target, routing configuration, and updated revision ID. This supplies a compare-and-set primitive for a direct alias controller. It does not establish that SAM/CodeDeploy accepts the same precondition from callers. [UpdateAlias](https://docs.aws.amazon.com/lambda/latest/api/API_UpdateAlias.html).
- SAM deployment preferences support validation functions before/after traffic shifting and CloudWatch alarms. CodeDeploy supports gradual traffic deployment. [SAM DeploymentPreference](https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/sam-property-function-deploymentpreference.html).
- CodeDeploy rollback redeploys a previous revision as a **new deployment with a new ID**. Automatic rollback must be configured for failure or monitoring thresholds. [Rollback behavior](https://docs.aws.amazon.com/codedeploy/latest/userguide/deployments-rollback-and-redeploy.html).
- CodeDeploy `AlarmConfiguration.ignorePollAlarmFailure` defaults false: inability to retrieve alarm state stops the deployment. Setting it true permits progress without that observation. [AlarmConfiguration](https://docs.aws.amazon.com/codedeploy/latest/APIReference/API_AlarmConfiguration.html).
- `GetDeployment` returns status, errors, revision, and `rollbackInfo` containing rollback and triggering-deployment IDs. [GetDeployment](https://docs.aws.amazon.com/codedeploy/latest/APIReference/API_GetDeployment.html).

## Engineering recommendations and experiment implications

These are proposed requirements derived from the facts above, not claims that providers implement them automatically.

1. **Persist before dispatch.** Allocate a logical deployment operation ID and attempt ID, bind them to repository ID, workflow identity, expected workflow commit, artifact digest/version, target account/region/stack, approval, and expiry. Pass correlation as validated input and include it in `run-name`. Request run details using an explicitly tested API version. Persist the returned ID before ordinary polling.
2. **Reconcile uncertain dispatch.** Simulate accepted requests with lost responses, 204 compatibility responses, delayed visibility, and duplicate submissions. Search a bounded, paginated window and match correlation plus workflow/ref identity. Zero visible runs is not proof of non-acceptance. Multiple matches require a deterministic runner-side claim before mutation; a title match alone is not authority. Until proof exists, retain `dispatch_unknown` rather than automatically issuing another write.
3. **Protect the executor independently of application source.** Dispatch only an allowlisted, protected deployment ref; verify its resolved commit against the approved executor identity. Check out the approved application SHA for packaging in a separate stage. Do not grant an arbitrary user-controlled source workflow a deployment role. Pin external actions. Inspect the actual OIDC subject and environment branch policies before designing AWS trust conditions.
4. **Handle approval expiry at the write boundary.** Revalidate approval identity, target, artifact, current state, expiry, and any cancellation after environment/concurrency waits and immediately before claiming execution. Test expiry while queued, approval revoked while paused, and credentials surviving approval expiry. A workflow-side timestamp check alone leaves a check-to-call race; any hard expiry contract needs a precisely defined atomic authorization-consumption boundary. Existing AWS credentials do not by themselves implement application revocation.
5. **Serialize the cloud target.** Use a target-level durable ownership/fencing mechanism and repository concurrency as a secondary guard. Test two different repositories or workflows addressing the same stack, pending replacement/overflow, and an older approved run starting after a newer deployment. Avoid cancelling an executor after it has initiated cloud mutation as a substitute for rollback; reconcile provider state first.
6. **Promote a manifest, not a rebuild.** Build/package once, record source and executor SHAs, package SHA-256, template digest, dependency/tool versions, and exact S3 object versions. Test replacement of a same-key object and delayed production approval. The deployment stage must verify the manifest and use the approved bytes. For cross-region copies, preserve content identity and record the new location/version.
7. **Keep exact CloudFormation identity.** Derive stable create/execute tokens from the logical operation, use unique change-set names, and persist the returned ARN. Test lost create and execute responses, an already-executed change set, an obsolete/deleted change set, and no-change results. Never resolve “missing change set” by silently rebuilding and executing a different plan under old approval. Reconcile stack events with the token and inspect final stack state.
8. **Choose one alias owner.** Prefer SAM/CodeDeploy as the only normal traffic writer. Direct alias compare-and-set is an alternative primitive, not a second simultaneous controller. For a direct-controller experiment, inject an alias change after reading its revision and require 412 without overwriting the newer target. For SAM, validate how stack serialization and CodeDeploy surface competing changes instead of claiming an unsupported revision precondition.
9. **Measure rollback as its own operation.** Require positive synthetic health evidence and configured alarm behavior; distinguish unavailable evidence from a passing check. Capture original and rollback deployment IDs, query both, verify the final alias/version and stack condition, and retain a failure outcome if rollback fails. Test pre-traffic failure, post-traffic failure, alarm-fetch failure, runner death during shifting, and an explicitly failed rollback. Traffic rollback is not a claim that application data migrations or side effects were undone.

## Remaining live validation

The documentation establishes feasibility, not an end-to-end tested deployment. A disposable authorized target must verify the selected REST version's response shape, correlation visibility before runner startup, OIDC claims/trust denial cases, immutable-artifact promotion, change-set retry tokens, health checks, and rollback completion. No installed CLI/SDK version or account policy compatibility was verified in this research subtask. Treat a local fake-provider experiment as evidence of the proposed state machine only.
