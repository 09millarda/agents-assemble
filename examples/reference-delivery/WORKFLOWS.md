# Reference delivery workflow distribution

These files are a deployable example, not evidence of a live AWS qualification. No cloud resources have been created by this change. The root repository does not activate these workflows.

Use a dedicated example repository and owner-controlled AWS account in `eu-west-1`. Copy `workflows/{delivery,rollback,merged}.yml` to that repository's `.github/workflows/`. Keep `examples/reference-delivery` in the same relative path. Create a protected trusted workflow branch (for example `aa-delivery`) containing these files and retain its exact commit. Point immutable deployment profiles at that branch and SHA. This decouples trusted workflow code from the changing human-merged source commit. Updating the workflow branch requires new immutable profiles and new admitted authority.

Before admitting runs, the owner provisions dedicated staging and production reference stacks, records their API Gateway `/health` URLs, and registers matching immutable deployment profiles. This example requires these existing dedicated targets. It does not silently provision an unknown target during a run. Profile fields bind repository ID, workflow path/ref/SHA, environment revision, account, stack, health URL/status, previous healthy artifact and policy generation. Set `rollbackWorkflowPath` to `.github/workflows/rollback.yml` when configuring rollback. Production approval includes the exact profile digest, environment revision, policy generation, account, stack, source commit and artifact digest.

Configure repository variables `AA_SERVICE_URL`, `AA_ORGANIZATION_ID`, `AA_REPOSITORY_ID`, `AA_WORKFLOW_REF`; `aa-build` environment variables `AA_ARTIFACT_BUCKET`, `AA_BUILD_ROLE_ARN`; and staging/production environment variable `AA_DEPLOY_ROLE_ARN`. Use environment branch restrictions for the trusted workflow branch and required reviewers for production. The service URL must have a publicly trusted TLS certificate accessible from GitHub-hosted runners. It exposes signed GitHub endpoints; runner certificates are not used by workflow jobs.

The artifact S3 bucket must have versioning enabled, be in `eu-west-1`, and deny this workflow deletion of retained object versions. The build role may upload only its retained-build prefix and read bucket versioning; it must not deploy stacks. Deployment roles may read exact retained object versions, operate only the dedicated stack/change sets and its Lambda/API/IAM resources, inspect Lambda code versions, and pass only the dedicated execution role where configured. Bind GitHub OIDC trust to audience `sts.amazonaws.com`, the exact repository and the appropriate protected GitHub environment. Do not give the build environment production-role trust. Use AWS access analysis to verify the final account-specific resource policy before enabling the target.

The human merge notifier reads the service delivery marker from the merged PR and dispatches `delivery.yml` on the configured trusted ref. The build job separately checks out the exact merge commit, installs its locked dependencies, builds once, includes its SAM template in the Lambda ZIP, computes SHA-256, uploads one versioned S3 object, and submits signed provenance. The service checks the actual mapped merged PR before accepting the release. No model output can register a release on its own.

The standalone `npm ci && npm run build` includes the project Apache license and notice, complete installed Hono and Zod license texts, and linked bundle legal comments in `dist/`; the workflow retains all of them in the Lambda ZIP. The build checks esbuild's actual dependency inputs and fails if a bundled package lacks an explicit license entry. Copying this example requires no root workspace dependencies or notice generator.

Deployment jobs consume one finite service claim, read the exact retained manifest, assume their own environment role with OIDC, download the retained ZIP/version and verify both ZIP and included template digests. They create one named CloudFormation change set and execute it once with the effect ID as the provider token. A failed response leads only to lookup of that same change set; it never triggers a second write. AWS automatic retries are disabled. Unknown workflow termination is retained for reconciliation; rerunning a job cannot consume another claim. The job verifies the actual versioned Lambda code digest and exact API Gateway health response before sending its signed receipt. Staging and production reuse the same ZIP; neither rebuilds it.

After CloudFormation completion and exact Lambda code verification, a failed health connection or the 15-second observation timeout is recorded in a signed unhealthy receipt with no invented HTTP status. Independent health verification records the same bounded failure as immutable evidence so the configured recovery policy can run. A failure before deployment/code verification still requires provider reconciliation.

Rollback uses the same client with a separately admitted recovery effect, the configured rollback workflow and the retained previous ZIP/template/configuration. It can supersede only the failed environment generation named by the recovery plan. A signed receipt and independent exact health verification establish `rolled_back`; missing prior artifact/configuration/authority or failed verification produces manual recovery evidence. A lost provider response remains uncertain and does not authorize a fresh attempt.

The workflow client's subprocess errors are reduced to stable failure classes; credentials and OIDC tokens are never printed. The source build runs before build-role credentials are acquired. Do not enable shell tracing around OIDC or AWS operations.

Protocol conformance uses a real HTTP GitHub/OIDC fixture and real signed job identities in `apps/api/src/integrations.test.ts`. Live AWS and real GitHub workflow qualification require the explicitly configured target above. The reference service has a local request test and a build check.
