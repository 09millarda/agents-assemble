# Throwaway signed GitHub OIDC / durable claim probe

Decision #15. Real GitHub-issued tokens are signature/issuer/audience/time verified with pinned `jose@6.2.12` before a local HTTP gate invokes the retained PostgreSQL claim worker. This is **not** the full AWS bridge. No AWS requests occur in this fixture.

The trusted GitHub job hosts the caller, gate and PostgreSQL service together. It seeds accepted authority and a staging receipt. Its expected repository/workflow/run policy is trusted setup, not an independently authenticated dispatch registry. It cannot establish separation from a hostile runner, the real Human Interaction acceptance flow or credential-to-provider enforcement.

Run `python3 experiments/deployment-oidc/verify-evidence.py` from this scratch checkout for read-only archive verification. Runtime source is pinned at `6c845240184ea9217dc45de3278a1ce7b0bdf46f`; main workflow revision is `129fba802e6dd55865317eb32cac29e84e63658e`. [Actual run 34770046279](https://github.com/09millarda/agents-assemble/actions/runs/34770046279) passed all seven scenarios with Node 22.23.2, PostgreSQL 17.9 and pinned package-lock dependencies. The workflow is disabled.

For a new live run, the main-branch workflow `.github/workflows/deployment-oidc-claim-probe.yml` supplies the temporary PostgreSQL service and GitHub OIDC environment, installs both this directory and `../deployment-authority` via `npm ci --ignore-scripts`, then runs `node probe.mjs` here. It is a mutating GitHub probe; archive verification does not re-enable it or dispatch anything. GitHub cleans up its hosted runner/service after each job.

The gate checks the real token's signature using only GitHub's fixed JWKS URL, issuer, exact scalar custom audience, RS256, timestamps and exact configured execution claims. It derives run/attempt from those verified claims. Body fields are restricted to registered effect ID and digest; the complete manifest comes from the owner record. The selected effect's approved workflow revision is separately checked before claim.

Seven scenarios cover actual verification, changed expected execution policy, absent/tampered/wrong-audience tokens, changed digest/caller-selected run, an effect approved for another workflow, duplicate HTTP requests/token replay and revoked authority. Concurrent requests yield one durable claim/outbox record. Wrong-repository/workflow/run policy tests change the verifier's expected values; they do not originate from another real repository or workflow. The wrong-audience token is actually issued separately by GitHub; the tampered payload is deliberately altered under the original signature.

Only allowlisted decoded claims, outcomes and database snapshots are retained. JWTs and OIDC request credentials are never printed, placed in the worker command/environment or written into evidence. `initial-result.json`/`initial-run.json` retain the earlier passing six-case run at source `ce9893f04ad0a3c83c6ab13428d941763398ef00`/workflow `a938cc3822e9fab63ae0b82c966fd232aa10f5ef`; review then exposed the missing effect-specific workflow comparison. The final seven-case run adds and proves that rejection.

Remaining limits include effect-specific dispatch registry/tenant permissions, authenticated human approval, JWT expiry during a body/lock wait, key-rotation/JWKS failure behavior, HTTP lost-ack recovery and a separate-host AWS controller. JWT time validity is checked at initial request authentication; product authority is checked under the database lock. The generic HTTP error path is not an unknown-commit reconciliation protocol. Existing worker rejection journals also retain their documented rollback-to-journal crash gap. See the independent audit and main research reports for scope.
