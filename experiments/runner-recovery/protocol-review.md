# Independent review: customer-runner recovery protocol

Date: 2026-09-12. Scope: supporting review for the single claimed Wayfinder decision [#8](https://github.com/09millarda/agents-assemble/issues/8). This file is disposable experiment evidence, not another decision or a production specification.

Inputs: ADR 0001, ADR 0003, `docs/research/runtime-failure-review.md`, `docs/research/durable-execution-conformance.md`, and issue #8. The requirements below are design deductions from those accepted boundaries. They do not assert untested harness, transport, identity, Git-host, or operating-system capabilities.

## Verdict before experiment review

The minimum useful contract has **three separate acceptance boundaries**: Execution commits a finite invocation grant; the daemon commits receipt and its local launch obligation; Execution commits acceptance or rejection of a generation-bound result. A tunnel receipt, native request ID, terminal event, or daemon journal record cannot stand in for any other boundary. Native launch remains outcome-unknown across the durable-journal/process-start gap unless the selected harness provides a demonstrably usable stable invocation lookup. Recovery must preserve that uncertainty rather than silently creating a second native invocation.

The portable recovery claim is a fresh, authorized invocation from independently fetched and verified inputs. Native session continuation is an optional measured capability. A stopped local process and a current server generation still do not establish that direct external effects are absent.

## Prioritized minimum requirements

### P0 — required for a safe protocol verdict

1. **Bind authority and identity before dispatch.** Execution commits a grant before making it deliverable. The grant identifies protocol version, tenant/deployment, runner, run/occurrence, attempt, assignment generation, invocation ID, command ID, payload digest, frozen input-manifest digest, declared attempt/recovery class, finite expiry and permitted operations. Runner identity is authenticated separately from the supplied runner ID; a payload hash proves equality, not authorization or provenance. The granting transaction remains Execution-owned and charges a new native invocation once.
2. **Durable daemon receipt precedes acknowledgment and launch.** One transactional local journal owns received-command identity/digest, immutable grant, local verdict and pending responses. Duplicate receipt returns the stored verdict without repeating launch; changed payload under the same scoped ID conflicts. Rejected commands remain rejected on replay. Crash-safe persistence needs explicit durability settings, single-writer locking and an identified recovery behavior if the journal is missing/corrupt. An in-memory map or append without a demonstrated flush boundary proves less.
3. **Do not close the native launch gap with a boolean.** Commit a launch obligation/uncertain dispatch state before invoking the harness. A crash before sending, while sending, after native acceptance, or before saving the native session/turn ID is not generally distinguishable after restart. Persisting `started=true` before launch avoids blind duplicate launch but can strand work; persisting it after launch risks duplication. An exact supported native lookup may settle the ambiguity; otherwise report `native_start_unknown`, obtain scoped stopped-writer evidence, reconcile effects, and require a fresh bounded recovery admission. Session creation and actual turn/inference admission are distinct operations.
4. **Replay results until Execution's own verdict is durable.** Store the terminal result/checkpoint reference and outbound result ID before transmission. Execution authenticates the producer, deduplicates the scoped identity/digest and validates current generation/lease/input scope in its own transaction. An acknowledgment lost after that commit returns the prior verdict even if the lease later expires; a new stale result cannot mutate current state. Only an acknowledgment referring to the exact result/digest and committed verdict permits ordinary local delivery completion. Terminal deltas are not canonical completion evidence.
5. **Reconnect reconciles durable identities, never infers a new run.** Re-authenticate the connection and compare known grants, local state, pending results and server verdicts. A browser attachment or replayed start command cannot admit work. A new tunnel/connection epoch must not allow an old connection to replace newer state, and delayed stop messages cannot stop a successor. No server record plus a local uncertain launch is a recovery obligation, not permission to start again. Define journal/inbox retention and what happens to messages older than retained history.
6. **Fence server writes and account for local writers separately.** Execution checks its generation and database-time lease. The daemon applies a conservative local disconnected-work deadline with a documented reboot/suspend/clock-skew behavior; that deadline is cooperative, not evidence of termination. A stop receipt includes run, attempt, generation, invocation, native session/turn if known, daemon/process identity and observed stop scope. Signal delivery, a missing PID, socket closure, `interrupt` request acceptance and lease expiry are not equivalent to a verified writer exit. Delayed evidence for an old generation may remain audit evidence but must not clear a replacement's obligations.
7. **Preserve cancellation and effect accounting as independent obligations.** Cancellation durably stops future admissions and requests accounting of accepted work. Report requested, stopping, stopped-with-scope, and outcome-unknown where justified. Do not declare complete cancellation while known accepted provider effects or writer uncertainty remain unaccounted. A terminal native interruption can coexist with a completed file write or already accepted provider operation. A server fence cannot revoke credentials or undo an accepted request. Recovery must not clear workspace uncertainty, publication uncertainty, cancellation and event gaps as a group.
8. **Verify checkpoints through the recovery consumer's access path.** Persist a manifest with run/attempt/generation, playbook and spec/input digests, repository identity, **original failing baseline commit separately from recovered working commit**, immutable Git object identity and durable ref, mandatory artifact identities/content hashes, accepted decisions/approval scope, environment-profile receipt, requested/effective harness settings, completed effects and unresolved outcomes. Required content must be durably published before marking the checkpoint resumable. A separate clean clone/fetch and artifact read verifies both commits, content and pinned scope; producer-local object existence or `verified: true` is insufficient. Push-success/ack-loss requires remote lookup/fetch reconciliation. A moving branch name alone is insufficient.
9. **Fresh reconstruction is fresh admission.** Before admitting the replacement, verify checkpoint availability/content, repository and frozen-input identity, required recovery class, environment policy and adapter capability. Recover the working checkpoint while preserving the original failure baseline for its intended later comparison. Use a fresh invocation ID and bounded allowance; exact replay does not charge again. Do not inherit a prior native turn's authority merely because its workspace can be restored. Missing artifacts, wrong digest, wrong pinned input, unsupported recovery class or unknown old writer/effect becomes a named pause condition.
10. **Honor native local authentication without substitution.** The selected harness must run under the intended OS identity and use its documented native login. Discovery/status, successful authenticated model invocation, restart/resume, and reauthentication are separate compatibility observations. Record exact executable/interface/version, effective settings and auth mode without credentials. Expired/missing login reports local reauthentication required; do not switch to an API key, copy account tokens, use a different service account, or silently substitute a provider/model. A working interactive-user probe does not certify a system service, container or another OS identity.

### P1 — contract detail required before product readiness, potentially outside this bounded prototype

- Journal schema migration, replay retention, disk-full/torn-write handling and recovery after losing the daemon disk; conservative startup locking if two daemons share the same runner identity.
- Run-scoped permissions and tenant isolation on every assignment, result, cancel, terminal and artifact path; revocation during a live tunnel; nonce/session replay and connection-epoch rules.
- Requested/effective model, effort, approval and sandbox settings in the checkpoint; capability negotiation must block or explicitly select a fallback rather than silently weaken behavior.
- Controlled payload/log upload and secret exclusion; daemon enrollment credentials isolated from native harness children and untrusted repository tooling by an actual process/security boundary. A Git worktree is not containment.
- Checkpoint retention and garbage collection; Git LFS/submodule content and external build inputs when declared; independently retrieved artifact content must match approved scope as well as hashes.
- Provider-specific provenance and reconciliation for actual PR publication: authenticated immutable Execution intent, integration-owned acceptance, verified destination/delivery mapping, exact reviewed commit, stable effect identity, durable receipt, and authoritative resolution of timeout/receipt loss. The #7 trusted provider fixture establishes none of those live-provider guarantees.

## Adversarial acceptance cases beyond #7's trusted boundaries

| Priority | Fault or adversarial input | Required observable verdict |
| --- | --- | --- |
| P0 | Kill daemon before durable receipt, after receipt before acknowledgment, and replay the same grant after restart. | No launch before receipt commit; persisted acceptance returns the original verdict; at most one permitted local launch path for one invocation. |
| P0 | Kill after recording the launch obligation but before spawn; separately kill after spawn/native acceptance but before saving IDs. | Both can remain explicitly launch-unknown unless independent native/process evidence distinguishes them. No automatic new `turn/start`. |
| P0 | Deliver same command/result ID with altered payload, runner, generation or input manifest. | Conflict/authorization rejection with no extra invocation or state mutation. |
| P0 | Lose native start response and reconnect the transport twice. | No duplicate native admission from reconnection; evidence identifies exact session/turn or recovery pauses. |
| P0 | Native finishes; kill daemon before result journaling, then after journaling; lose server acceptance acknowledgment. | Before journaling: infer completion only from verified native/artifact evidence. After journaling: replay the same result. After server commit: return prior verdict without repeating invocation or charging work. |
| P0 | Expire grant during partition; admit generation N+1; restore N with delayed result, cancellation and stopped-writer receipt. | Stale messages cannot complete/cancel/stop N+1 or grant fresh effects. N's unresolved effects remain attributable. |
| P0 | Deliver interrupt successfully while a descendant tool continues, or lose the interrupt response. | Scope-limited stop evidence or stop-unknown; no broad assertion that every writer/effect stopped. |
| P0 | Reuse a PID after daemon restart or reboot; send a prior process's stop receipt. | Stable boot/process/supervisor evidence prevents treating an unrelated PID as the old writer; uncertainty remains explicit when unavailable. |
| P0 | Kill checkpoint before push, after push before receipt, and after manifest commit; move/delete required ref. | Incomplete checkpoint is unavailable; successful orphan reconciles by immutable object/content; missing retained content blocks recovery. |
| P0 | Supply recovered working commit as the original baseline, change input manifest, or supply artifact bytes with correct-looking metadata but wrong digest. | Reject wrong baseline/scope/content; do not overwrite original failure input or trust metadata flags. |
| P0 | Remove one required artifact or deny consumer access while leaving producer access intact. | Recovery blocks with the exact dependency/access reason before fresh admission. |
| P0 | Attempt reconstruction with undeclared recovery class, exhausted cap, wrong runner capability or revoked environment input. | No replacement native invocation; exact replay cannot double-charge or bypass a rejection. |
| P0 | Supply forged `transportVerified`, `verified` or approval text in a legitimate issue/artifact. | Content cannot grant authority; authenticating/verifying adapters must establish those facts independently. A trusted fixture must label this case unproved. |
| P0 | After lease expiry/stop, use retained Git/provider credentials from the old machine. | Demonstrate/report writes still possible unless real downstream controls enforce revocation. Do not infer physical fencing from server rejection. |
| P1 | Run two daemons with same identity/journal, corrupt/drop the journal, or redeliver past dedupe retention. | Reject concurrent ownership or enter explicit recovery; never treat an empty/unknown journal as proof the command did not execute. |
| P1 | Revoke enrollment or cross tenant/runner IDs during established terminal/result/artifact connections. | Authorization rechecked at the relevant access boundary; a connection is not perpetual authority. |
| P1 | Native login unavailable/expired under actual service identity; reauthenticate natively and repeat. | Actionable local-auth state; original native account mechanism restored; no credential extraction/substitution. |
| P1 | Fetch checkpoint in a new directory but accidentally share producer object alternates or local-only artifact storage. | Record that this is not independent availability proof; repeat with consumer-only upstream/dependency access. |

## Evidence claims that must remain separate

| Claim | Minimum supporting observation | What it still does not prove |
| --- | --- | --- |
| Native-account compatibility | Exact installed interface successfully invokes the existing native login under recorded OS identity. | Login expiry/repair, unattended startup, other identities/versions/harnesses, account eligibility everywhere. |
| Durable receipt/result replay | Real persisted local journal and killed/restarted process preserve stable verdicts across the stated boundaries. | Durable disk/controller guarantees, corrupt storage, complete SQL Execution integration, arbitrary concurrent schedules. |
| Stopped writer | Verified terminal native/process state plus explicitly stated ownership/descendant scope. | Unseen detached descendants, prior downstream acceptance, provider-side cancellation or revoked credentials. |
| Verified checkpoint | Independent consumer fetch/read verifies exact baseline/working objects, mandatory artifacts and frozen input hashes. | Complete hermetic builds, origin authenticity from hashes alone, Git-host authorization/retention beyond the fixture, LFS/submodules unless exercised. |
| Reconstruction | Fresh eligible invocation admitted once from verified manifest under declared recovery class. | Native transcript migration, equivalent reasoning, recovery on another physical machine or OS unless actually run there. |
| Intent/receipt authenticity | Authenticated adapters bind the issuer, audience, immutable manifest/effect and actual downstream receipt. | Nothing from a trusted boolean/provider fixture can establish this production claim. |
| Direct-credential safety | Actual destination enforces tested credential revocation/scoping and effect reconciliation. | Server generations alone provide no such enforcement. |

## Review of actual source and results

### Native source and recorded evidence

Inspected `native/probe.py`, `native/results/results.json`, both native lifecycle traces, the archived Git bundle/manifests/diffs, `native/kill_boundary.py`, and `native/kill-results/results.json`.

The reference is **Codex CLI 0.153.4, app-server over stdio JSON-RPC, Linux x86_64, existing native ChatGPT authentication under the current OS user**. The child environment is explicitly allow-listed and excludes inherited provider API keys and host session tokens. The local native interface reports effective workspace-write, no tool network and approval policy `never`; requested model/effort are omitted, and the effective settings are recorded. A successful account-status call is complemented by completed native turns with real safe local edits and tests. This supports this installation/account/interface, not a general subscription or system-service certification.

The first native turn fixes the actual preserved failing arithmetic baseline (two original test failures become three passes). The independent verification then reconstructs the working Git checkpoint in a fresh clone and supplies a hashed manifest to a different ephemeral native thread; the continuation adds the intended operation and all seven tests pass. No native transcript is copied. The manifest's fresh-grant value is trusted fixture data, not an integrated Execution admission.

Independent archive/integrity script `review-native-check.py` passed **25 assertions** without further inference. It verifies bundle and manifest hashes, clones the self-contained archived bundle without Git object alternates, reproduces the original failures, checks baseline ancestry and exact checkpoint content, applies the archived recovery diff and runs all seven tests. The original native run's recovery test was untracked and its original assertion only checked tracked diffs. Review identified that gap; a post-run check proved the retained recovery test exactly equals the original fixture literal, with unchanged tracked test/manifest hashes and the exact declared untracked set. The probe source now records pre/post test hashes for future reproductions. This is an explicit post-run integrity audit, not a retroactive claim that the first run recorded hashes it did not record.

The actual kill probe establishes a useful negative result: an acknowledged `inProgress` turn and structured command start led to an unfinished local marker; the probe then killed the owned app-server with SIGKILL (exit -9). **Two observed descendants, including the uniquely correlated Python sleeper, remained alive one second after parent exit.** No terminal turn event was recorded. A fresh app-server could neither read nor resume the lost ephemeral thread; the probe made no automatic new turn. Recovery correctly remains dispatch-unknown. Exact observed descendant identities were cleaned up afterward, with zero of those identities remaining; this is not universal process containment or remote-effect accounting.

The first kill attempt failed before injection because the marker contained a namespace PID rather than a host PID. Its results are preserved separately in `native/kill-precondition-pid-namespace`; the corrected probe uses a unique observed Python descendant's `NSpid` mapping. Do not count the initial precondition failure as a reached SIGKILL experiment.

`TurnStartParams` contains an optional `clientUserMessageId`, but its generated type does not establish a deduplication or stable invocation-lookup guarantee. Native turn-start replay/idempotency, non-ephemeral same-session recovery, native auth expiry/repair and unattended service identity remain unproved.

### Daemon source review and adversarial verification

The source review identified and the fixture author repaired:

- A STOP/CONT barrier race. The controller now observes the worker's stopped state before continuing or killing it.
- A launch-state read outside the launch transaction. An OS file lock now rejects an actually overlapping second daemon process; invocation uniqueness is independent of command ID and generation.
- Recovery verification not bound to the command. The verifier now returns exact manifest and expected-input digests; admission checks both before granting the recovered invocation.
- Rejected commands/admissions that could later become accepted under the same command identity. Keyed durable verdicts now preserve exact rejection; repaired requests use fresh identities.
- Negative recovery decisions recorded without assertions. Rejections now have explicit assertions, including class, missing verification, mismatch, repeated attempt and exhausted budget.
- Missing payload-digest consistency at recovery admission. Self-inconsistent commands now fail before granting or charging work.
- A stop report whose current-looking outer fields could relabel an old embedded command/process binding. The service now requires matching nested/outer assignment identity and exact registered process-instance/PID correlation. These reports remain trusted fixture inputs; a matching value alone is not proof of a real stopped process.
- Root review additionally found that `/receipt` did not check its ID/digest against the issued grant and the worker ignored a negative acknowledgment. The final repair validates the issued grant, durably pauses on negative acceptance, checks the current attempt before launch and rejects historical attempt reuse explicitly.

The final daemon suite passed **26 scenarios**. After all repairs, independent `review-daemon-check.py` re-execution passed **25 assertions**: accepted-result replay after actual expiry and replacement, new stale result/changed payload rejection, a real consumer clone without alternates, persisted admission rejection, exact verification manifest/input binding, malformed digest, one budget charge, wrong process instance/PID and an old stop binding relabeled with a current envelope. The suite evidence, independent results and inspected source all match SHA256 `4e7634ac5e8f16bdec73c4eebf9d3252229614015be1568da7c7b449948e08f6`. These 25 assertions are separate from the main 26 scenarios and from the native archive/integrity audit's 25 assertions; they are not double-counted as native or integrated execution tests.

These independent checks deliberately use trusted synthetic result/admission/process reports. They add no native inference, process-containment, tenant/authentication or downstream receipt-provenance claim. The main daemon suite independently exercises real subprocess death, SQLite durability, HTTP response loss and Linux pidfd exit. Native behavior remains the separate evidence path described above.

Important remaining limits: the daemon fixture does not demonstrate restart-safe monotonic deadline conversion, remote Git push-success/ack-loss reconciliation, downstream credential revocation, an inaccessible external artifact store, secure grant/checkpoint authenticity, retention under remote garbage collection, or loss/corruption of the whole daemon disk. A fresh local clone or bundle proves the exercised Git content retrieval, not those omitted adapter guarantees.

### Recommended next sharp frontier

The native kill result makes **native writer supervision and stopped-writer accounting** the strongest immediate next decision: establish an enforceable process ownership/containment boundary and scope the evidence needed before automatic takeover. Authenticated tunnel/enrollment, exact GitHub publication intent/receipt provenance and provider reconciliation remain separate future work. Combining all authenticity concerns into one ticket would be too broad.
